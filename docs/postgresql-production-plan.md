# طرح پایگاه تازه PostgreSQL و فعال‌سازی سرور

وضعیت: **آماده بررسی مالک؛ اجرا روی سرور تأیید نشده و انجام نشده**. تاریخ: ۲۰۲۶-۱۰-۱۴.

## نسخه و مقصد

- SSH تأییدشده: alias `promty-production` با بررسی اجباری کلید میزبان؛ سایت `https://promty.ir`؛ مسیر فعال `/var/www/promty`.
- PM2 واقعی: `promty-backend`، cwd همان مسیر، اجرای `dist/server.cjs`؛ Node 20.20.2، npm 10.8.2 و package-lock نسخه 3.
- کامیت پیشنهادی: شاخه release، **dbb80f7309a944baa5d0f6bba110db1b36d4bedc**. فقط فایل‌های این کامیت، بدون تغییرهای مستندات جاری یا فایل‌های محلی.
- بسته محلی قابل بررسی: `/home/sajj/developing/promty/releases/postgres-cutover-dbb80f7/application.zip`؛ manifest و preflight کنار آن.
- SHA256 بسته: `599e328dd4d4ee9cd9ec294639edf6ec3663621c48a76ce3332bad1b684d3975`.
- ۸۴ فایل برنامه در بسته؛ db.json، .env و .env.example، رسانه، داده خصوصی و ابزارهای واردکردن demo/seed حذف شده‌اند. node_modules و Build محلی انتقال نمی‌یابد.
- hash فایل‌های واقعی سرور با نسخه مقصد مقایسه شد: ۶۶ فایل منطبق، ۱۸ فایل تغییرکرده/جدید؛ فهرست در preflight.json است. Git سرور به main و SHA `5132646fef1e22f9f304ef39d1e7f2ec2d9fc8c3` اشاره می‌کند اما object HEAD موجود نیست؛ منشأ Build فعلی اثبات نشده. git pull/reset/clean یا ترمیم خودکار آن جزو طرح نیست. روش پیشنهادی انتقال artifact دقیق، با حفظ نسخه فعلی، نیازمند تأیید مالک است.

## تصمیم داده

پایگاه تازه پیشنهادی: `promty_prod_v2` روی PostgreSQL موجود سرور، loopback:5432، نسخه 16.15. اگر نام پایگاه یا نقش پیشنهادی از قبل وجود داشته باشد، توقف؛ overwrite/reset/ادغام انجام نشود.

نقش مالک schema: `promty_owner_v2` بدون LOGIN؛ نقش برنامه: `promty_app_v2` با LOGIN و رمز جدید خصوصی، بدون SUPERUSER/CREATEDB/CREATEROLE/REPLICATION. نقش برنامه CONNECT، USAGE schema و دسترسی CRUD لازم دارد؛ مالک DDL نیست. نقش‌ها یا دسترسی پایگاه‌های دیگر تغییر نمی‌کنند.

داده‌های قدیمی به مقصد جدید منتقل نمی‌شوند: JSON فعال یک پرامپت و دو حساب دارد؛ پایگاه قدیمی promty_db تقریباً هفت پرامپت، سه preset و شش نشان دارد (تخمین آماری). هر دو محفوظ می‌مانند. پایگاه تازه با صفر محتوای منتشرشده و taxonomy استاندارد شروع می‌کند. اولین ورود با ADMIN_EMAIL/ADMIN_PASSWORD فعلی حساب ADMIN می‌سازد؛ SUPER_ADMIN_EMAIL اکنون برای این حساب تنظیم نیست و نقش مدیر ارشد خودکار اعطا نمی‌شود. نشست‌های قبلی با حساب‌های قدیمی در پایگاه تازه معتبر نخواهند بود.

تنظیمات سایت، لوگو، webhookها، روابط گراف، رسانه و state امنیتی فعلی حفظ می‌شوند؛ db.json هنوز برای این اجزا لازم است. نمونه‌های لوکال و داده‌های PostgreSQL قدیمی وارد Production نمی‌شوند.

## ترتیب پیشنهادی پس از تأیید صریح

۱. خواندن دوباره هویت مقصد، PM2 و cwd، وضعیت فایل‌ها/تنظیمات و فضای دیسک؛ تطبیق با preflight. سایر سایت‌ها/سرویس‌ها خارج از محدوده‌اند. تغییر مهم موجب توقف و طرح دوباره می‌شود.
۲. تهیه بکاپ خصوصی خارج از وب، زیر `/root/promty-backups/<timestamp>`، با پوشه 0700 و فایل‌های 0600: کد و Build و وابستگی‌های فعال، .env، db.json، dl، .private و مسیرهای خصوصی خارجی واقعی؛ dump پایگاه PostgreSQL قدیمی و نقش‌های مرتبط. خوانایی، hash و امکان restore بررسی شود. پیش از تغییر نسخه فعال، snapshot سازگار داده‌ها با توقف نویسنده‌ها در زمان نگهداری تأییدشده گرفته شود. نبود امکان backup/rollback مانع ادامه است.
۳. انتقال و کنترل hash بسته در پوشه candidate جدا؛ نصب `npm ci --include=dev` با lock همین کامیت، تولید Prisma Client و Build روی Node فعلی. مسیر، فضای دیسک و دسترسی قبل از نصب بررسی شوند؛ نسخه فعال تا موفقیت candidate دست‌نخورده است. هیچ فایل محیطی لوکال انتقال نمی‌یابد.
۴. ایجاد فقط پایگاه/نقش‌های تازه؛ تولید رمز در کانال خصوصی سیستم، خارج argv/log/docs؛ اعمال schema کامل تولیدشده از schema همین کامیت در تراکنش با توقف روی خطا؛ تنظیم مالکیت و grants محدود. SQL اتمیک تازه در لوکال آزموده شده است و کنار بسته در fresh-schema.sql قرار دارد. `prisma migrate deploy`، reset، seed و db push روی Production اجرا نشوند. اخطار یا وجود داده قبلی در مقصد باعث توقف است.
۵. در زمان نگهداری، توقف فقط `promty-backend`، snapshot نهایی، جایگزینی فقط فایل‌های برنامه در manifest و dist/node_modules ساخته‌شده با حفظ نسخه قبلی. .git، .env، db.json، dl و .private با بسته جایگزین نشوند. فایل غیرمرتبط حذف نشود؛ rsync --delete ممنوع.
۶. فقط DATABASE_URL در محیط واقعی برنامه و .env به مقصد تازه تنظیم شود؛ STORAGE_BACKEND=json، اگر ظاهر شد، پس از بررسی تضاد کنار گذاشته شود. JWT و اطلاعات مدیر/پیامک/webhookهای موجود حفظ شوند؛ LOCAL_PREVIEW خاموش و NODE_ENV=production باقی بماند. مقدار URL/رمز در گزارش چاپ نشود. پیکربندی PM2 و .env باید منطبق باشند تا restartهای بعدی هم PostgreSQL را انتخاب کنند.
۷. اجرای check-release روی schema و پیکربندی مقصد؛ سپس restart فقط سرویس واقعی با update-env. مسیر ثابت /var/www/promty و Gateway واقعی Nginx Proxy Manager حفظ شوند؛ PM2 save فقط پس از پذیرش سلامت، با حفظ برنامه‌های دیگر.
۸. بررسی لاگ جدید برای انتخاب Prisma و نبود fallback، وضعیت پردازش، API داخلی و از کانتینر پراکسی و HTTPS؛ آرشیو تازه باید صفر محتوای قدیمی/demo داشته باشد. ورود مدیر با اعتبارنامه موجود، چرخه ساخت→پیش‌نمایش خصوصی→انتشار→ویرایش→عدم انتشار، ثبت فارسی، فیلتر و رسانه آزموده شود. نوشتن فقط یک محتوای مشخص آزمایش پذیرش و حذف همان محتوای آزمایشی، اگر در تأیید مالک باشد؛ هیچ پاک‌سازی عمومی انجام نشود. آزمون مرورگر و پیامک واقعی موفق فرض نشود.

زمان قطعی دقیق قبل از اجرا تضمین نمی‌شود؛ نصب و Build پیش از توقف سرویس انجام شوند تا قطعی محدود به snapshot نهایی و تعویض نسخه/اتصال باشد. توقف کوتاه سرویس نیز باید در تأیید مالک پوشش داشته باشد.

## توقف و بازگشت

با شکست backup، install، Build، schema، مجوز یا health، مرحله بعد اجرا نشود و وضعیت واقعی گزارش شود. پایگاه تازه یا نقش‌های ساخته‌شده خودکار حذف نشوند. نسخه قبلی و محیط فعال برای بازیابی همان مسیر محفوظ باشند. بازگشت تنظیم DATABASE_URL/کد فقط با مجوز مالک و ارزیابی امنیت نسخه قبلی انجام شود؛ نسخه قبلی برای انتشار عمومی امن فرض نشود.

اگر بعد از فعال‌سازی داده تازه نوشته شد، پیش از بازگشت dump/export از پایگاه جدید گرفته و تطبیق شود؛ بازگشت کد به معنی بازگشت داده نیست. هیچ داده‌ای از قدیمی یا جدید حذف نشود. با قطع اتصال/timeout نتیجه عملیات قبل از تکرار خوانده شود.

## محدوده تأیید موردنیاز

مالک باید همین مقصد، SHA کامل، روش artifact (به علت Git خراب سرور)، ایجاد پایگاه/نقش‌های تازه بدون انتقال داده قدیمی، backup، تغییر محدود محیط، جایگزینی فایل‌های برنامه، توقف/راه‌اندازی مجدد فقط پرامتی و آزمون پذیرشِ دارای نوشتن را صریحاً تأیید کند. تأیید «داده قدیمی لازم نیست» به‌تنهایی تأیید اجرای این عملیات روی سرور نیست. هیچ Push یا تغییر main، حذف پایگاه قدیمی یا تغییر سرویس‌های دیگر جزو این طرح نیست.
