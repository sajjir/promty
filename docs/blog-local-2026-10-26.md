پس از تکمیل صفحات اعتماد، مالک گفت «گام بعدی رو شروع کن». این مرحله اجرای بلاگ طبق طرح قبلی در پیش‌نمایش لوکال است. Commit/Push، SSH، انتقال داده و استقرار روی Production در این مرحله انجام نشدند. تغییرات گام اول هنوز در working tree حفظ‌اند.

SQL افزایشی نسخه‌بندی‌شده: prisma/migrations/20261026_blog/migration.sql. فقط enum، دو جدول، indexها و foreign keyهای جدید را می‌سازد. relation حذف پرامپت فقط پیوند آن را حذف می‌کند، نه مقاله را. SQL در تراکنش با محدودیت زمان قفل روی مقصد صریح 127.0.0.1:55432/promty_local اعمال شد. reset، db push، migrate dev یا حذف داده اجرا نشد. تاریخچهٔ مهاجرت قدیمی پروژه baseline کامل نیست؛ این SQL با ابزار مهاجرت عمومی روی سرور اجرا نشود.
بکاپ خصوصی و گزارش اعمال در /home/sajj/developing/promty/releases/blog-local-2026-10-26/ هستند؛ dump hash و pg_restore --list/خواندن SQL تأیید شدند. restore کامل پایگاه از dump آزمایش نشد. تعداد پرامپت‌ها و کاربران قبل و بعد از افزودن جدول‌ها برابر بود. هیچ رمز یا URL اتصال در این سند نیست.

## محتوا، امنیت و API
- slug انگلیسی یکتا؛ پس از اولین انتشار ثابت. تاریخ نخستین انتشار از ساعت سرور و پس از انتخاب PUBLISHED تعیین می‌شود؛ تاریخ دلخواه کلاینت پذیرفته نمی‌شود. برداشتن از سایت با DRAFT، داده را نگه می‌دارد.
- API عمومی فقط PUBLISHED با publishedAt<=now می‌دهد، حتی اگر درخواست‌کننده مدیر باشد. مقالهٔ پیش‌نویس مستقیم 404/noindex است. فهرست عمومی صفحه‌بندی ۱۲تایی دارد؛ صفحهٔ خارج محدوده 404 است.
- get عمومی فقط پرامپت فعال را به مقاله متصل می‌کند. شناسهٔ کارت‌های غیرفعال از متن عمومی shortcode نیز کنار گذاشته می‌شود. جزئیات حساس پرامپت مانند editorial/sourceText در DTO مقاله وجود ندارند. نمایش خصوصی فقط در endpoint مدیریت و پیش‌نمایش فرم انجام می‌شود.
- API مدیریت از همان احراز هویت واقعی و نقش مدیر/مدیرکل و کنترل Origin پروژه استفاده می‌کند. رشته‌ها و طول/تعداد فیلدها اعتبارسنجی می‌شوند. کنترل updatedAt در write شرطی و تراکنش از بازنویسی ویرایش هم‌زمان جلوگیری می‌کند؛ timestamp جدید همیشه از قبلی بزرگ‌تر است. تکرار slug و نسخهٔ کهنه 409 می‌دهند. حذف دائمی مقاله به UI اضافه نشده است؛ حذف تکی/گروهیِ قابل بازیابی طبق درخواست بعدی مالک در بخش زیر اضافه شد.

## Markdown و نمایش
markdown-it 15.0.3 با html:false و سیاست محدود URL؛ HTML خام متن می‌شود و اجرا نمی‌شود. javascript/data/file/vbscript و URLهای // و URLهای دارای اطلاعات ورود/کاراکتر کنترلی پذیرفته نمی‌شوند. sanitizer وابسته به DOM یا HTML خام مشترک مرورگر/سرور نداریم؛ همان parser امن در هر دو استفاده می‌شود. [راهنمای امنیت خود کتابخانه](https://github.com/markdown-it/markdown-it/blob/master/docs/safety.md).
تیترها ID تولیدشده با پیشوند blog-heading دارند؛ H1 متن به H2 تبدیل می‌شود تا عنوان مقاله H1 اصلی بماند. فهرست مطالب از H2/H3 ساخته می‌شود. بلوک کد dir=auto دارد. shortcode فقط در یک خط مستقل و بیرون code fence/متن درون‌خطی/فهرست تو‌در‌تو تفسیر می‌شود.
کارت سبک میان متن و انتهای مقاله به صفحهٔ واقعی شخصی‌سازی پرامپت می‌رود؛ wizard یا اجرای هوش مصنوعی در خود مقاله جاسازی نشده است. در صفحهٔ پرامپت نیز آموزش‌های منتشرشدهٔ مرتبط نشان داده می‌شوند.

## سئو و رسانه
/blog و /blog/:slug در React و renderer موجود سرور پشتیبانی شدند. BlogArticle/BlogIndexContent مشترک، متن کامل اولیه، Canonical، BreadcrumbList، Article یا CollectionPage واقعی و Open Graph مقاله دارند. نویسنده و تاریخ‌های نمایش‌داده‌شده مبنای Schema هستند؛ FAQPage و امتیاز ساختگی نداریم. مقالهٔ منتشرشده و تصویر کاور معتبر وارد sitemap می‌شوند؛ draft و تاریخ آینده حذف‌اند. جستجوی درون بلاگ/نظرات/خبرنامه در این مرحله ساخته نشدند.
کتابخانهٔ رسانه اکنون ارجاع کاور و تصویر Markdown مقاله را می‌شناسد. رسانهٔ draft فقط برای مدیر است؛ با انتشار عمومی و با برداشتن از انتشار مجدداً خصوصی می‌شود. رسانهٔ مورداستفادهٔ مقالهٔ منتشرشده یا draft از کتابخانه حذف نمی‌شود. فایل‌های قدیمی و تصویرهای کاربر حفظ شدند.

## انتشار بعدی و بازگشت
برای انتشار واقعی، SHA نهایی، diff، backup PostgreSQL/فایل‌ها، اجرای همین SQL افزایشی و ترتیب تولید Prisma Client/Build/check-release باید در طرح جدید سرور تأیید شوند. پایگاه Production را seed/reset نکنید و دادهٔ لوکال را خودکار منتقل نکنید. در برگشت کد، جدول‌های دارای مقاله حذف نمی‌شوند؛ بازگشت داده نیازمند طرح جداست. تکمیل مدیریت انتشار با محتوای واقعی همچنان نیازمند بازبینی تحریریه است.


## تکمیل طبق درخواست بعدی: حذف تکی و چندانتخابی
مالک در حین همین مرحله خواست مقاله در داشبورد قابل حذف و چندانتخابی باشد. ستون nullable deletedAt و index آن با migration افزایشی 20261026_blog_trash اضافه شدند. پیش از اجرای SQL فقط روی PostgreSQL لوکال، بکاپ تازهٔ خصوصی backup-before-trash.dump گرفته و خوانایی آن تأیید شد؛ هیچ مقاله‌ای در مهاجرت حذف/ویرایش نشد و تعداد کاربران/پرامپت‌ها/مقاله‌ها ثابت بود. برای اولین انتشار روی سرور، هر دو SQL بلاگ و سطل زباله در ترتیب نسخه لازم‌اند؛ هیچ‌کدام در این مرحله روی سرور اجرا نشده‌اند.

فهرست ادمین چک‌باکس تکی، انتخاب همهٔ همین صفحه، شمارنده، حذف انتخاب‌شده‌ها و حذف هر ردیف دارد. حذف به سطل زباله می‌رود و مقاله از API عمومی، HTML، sitemap و آموزش مرتبط حذف می‌شود. بازیابی تکی/گروهی همیشه DRAFT برمی‌گرداند؛ انتشار دوباره نیازمند اقدام مدیر است. کاور و تصاویر متنِ مقالهٔ حذف‌شده در شمارندهٔ مصرف رسانه محفوظ می‌مانند تا از بین‌رفتن فایل مانع بازیابی نشود، ولی خود مقالهٔ حذف‌شده هیچ رسانه‌ای را عمومی نمی‌کند.

API DELETE /api/admin/blog و POST /api/admin/blog/restore تنها برای مدیر هستند. حداکثر ۱۰۰ شناسه همراه نسخه‌های updatedAt پذیرفته می‌شوند. عملیات در تراکنش است؛ یک نسخهٔ کهنه کل درخواست را با 409 رد می‌کند و هیچ حذف/بازیابی ناقصی انجام نمی‌شود. ذخیرهٔ مستقیم مقالهٔ داخل سطل زباله نیز 404 است تا از دورزدن بازیابی جلوگیری شود.

آزمون PostgreSQL/HTTP مستقل بعد از افزودن سطل زباله دوباره موفق شد: منع نقش عادی و ناشناس، رد اتمیک درخواست چندتایی کهنه، حذف دو مقالهٔ منتشرشده، خروج از سایت و خصوصی‌شدن تصویر، حفظ رسانهٔ قابل بازیابی، بازگردانی دو مقاله به draft و حذف تکی. تنها دادهٔ fixture در schema موقت حذف شد. در مرورگر دو انتخاب و سپس انتخاب همهٔ چهار نوشتهٔ همان لحظه، فعال‌شدن دکمهٔ گروهی، پاک‌کردن انتخاب و ورود به سطل زباله بررسی شدند؛ هیچ مقالهٔ واقعی با مرورگر حذف نشد. تصویر admin-multi-delete.jpg در پوشهٔ شواهد همین مرحله است.
