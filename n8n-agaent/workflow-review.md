# بررسی ورک‌فلوی promty

تاریخ: ۲۰۲۶-۱۰-۱۷. منبع: `promty.json` و تصویر ارسالی مالک، در تطبیق با کد پرامتی در کامیت `7e06770` برنچ `release`.

## نتیجه

تفکیک مسیریابی، تولید تخصصی و بازبینی برای این محصول قابل استفاده است؛ اما کیفیت فعلی فقط با کوتاه‌کردن پرامت‌ها اصلاح نمی‌شود. چند ناسازگاری اجرایی و چند دستور متناقض، خروجی را پیش از نمایش در سایت خراب یا نامطمئن می‌کنند. در این مرحله اصل نسخه‌ها آرشیو و ایرادها بررسی شده‌اند؛ نسخهٔ اصلاحی هنوز اعمال نشده است.

## مسیر واقعی

`Webhook → RouterNode → RouteSwitch → یکی از Design/programming/general → QA/Verifier → Code in JavaScript1 → Respond to Webhook2`

- در فایل ۱۱ نود وجود دارد: پنج نود پردازش متنی با مدل، یک مدل مشترک، یک parser مسیریاب، یک Switch، یک Code و دو نود وب‌هوک.
- RouterNode از نوع Basic LLM Chain است؛ چهار نود دیگر از نوع AI Agent هستند. ابزار و حافظه‌ای در اتصالات export به آن‌ها وصل نشده است.
- هر درخواست عادی سه مرحلهٔ پردازش با مدل دارد: مسیریاب، یک متخصص، QA. این تعداد مرحله است؛ retry یا فراخوانی داخلی runtime اندازه‌گیری نشده است.
- هر پنج نود به `Google Gemini Chat Model2` با مقدار `models/gemini-3.1-flash-lite-preview` وصل‌اند؛ options صریح مدل خالی است. کیفیت، دسترس‌پذیری و زمان این مدل آزمایش نشده است.
- فقط RouterNode خروجی parser متصل دارد. QA و متخصص‌ها با دستور متنی موظف به JSON شده‌اند.
- تصویر اجرای شاخهٔ Design را نشان می‌دهد؛ فایل هیچ نمونهٔ pin‌شده یا خروجی اجرای واقعی ندارد.

## ایرادهای اولویت بالا

### ۱. قرارداد ناسازگار خروجی مسیریاب در Switch

شاهد: [RouteSwitch و RouterOutputParser](workflow-settings.md).

دو شاخه از `$json.output.routing_category` استفاده می‌کنند، اما شاخهٔ general از `JSON.parse($json.output).routing_category`. این دو انتظار با هم سازگار نیستند: اگر output شیء باشد، general در JSON.parse خطا می‌دهد؛ اگر رشته باشد، دو شاخهٔ دیگر مقدار مورد انتظار را نمی‌خوانند. هر دو حالت در JavaScript محلی بازآفرینی شد؛ اجرای خود n8n انجام نشده است.

پیشنهاد: خروجی مسیریاب یک‌بار به شکل شیء اعتبارسنجی شود، هر سه قانون یک مسیر داده و مقایسهٔ دقیق `equals` داشته باشند. programming اکنون `contains` دارد. مقادیر ذخیره‌شدهٔ `=design` و `=programming` باید در preview همان نسخهٔ n8n بررسی و با مقدارهای ثابت روشن یکسان شوند؛ صرف وجود `=` در export به‌تنهایی اثبات خطا نیست.

Switch هیچ fallback صریحی ندارد؛ طبق [مستند رسمی Switch](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.switch/)، مقدار پیش‌فرض مورد بدون تطابق را کنار می‌گذارد. در نتیجه مسیر معمول پاسخ نهایی برای آن مورد طی نمی‌شود؛ شکل پاسخ نهایی HTTP باید در runtime بررسی شود. خروجی خطای مشخص برای category نامعتبر لازم است.

### ۲. Code متن اصلی را تغییر می‌دهد و اعتبارسنجی کافی ندارد

شاهد: `jsCode` در [تنظیمات](workflow-settings.md) و [بازآفرینی محلی](verification.md).

جایگزینی سراسری `/```json/gi` و `/```/g` روی رشتهٔ JSON، حصار بلوک‌های داخل مقدار `body` را هم پاک می‌کند. نمونهٔ سالم پرامت برنامه‌نویسی بدون خطای parse با متن تغییریافته برمی‌گردد؛ برخلاف دستور حفظ عین کد در programming.

همچنین این نود `{title: ...}` بدون body/schema یا فیلدهایی با نوع اشتباه را می‌پذیرد و تنها برای عنوان و tags مقدار پیش‌فرض می‌گذارد. خروجی شیء مستقیم، بدون wrapper `output/text`، پذیرفته نمی‌شود. تبدیل به Structured Output در آینده بدون هماهنگی این نود می‌تواند مسیر را بشکند.

پیشنهاد: object یا رشتهٔ JSON طبق قرارداد مشخص خوانده شود؛ ابتدا parse مستقیم، و فقط در صورت نیاز حذف حصار بیرونی کل پاسخ. سپس نوع فیلدها، گزینه‌های مجاز، یکتایی key و تطابق متغیرها/schema با کد قطعی بررسی شوند. نقص داده با عنوان عمومی پنهان نشود.

### ۳. نمونهٔ JSON در Design نامعتبر است

شاهد: بخش `EXPECTED JSON SCHEMA` در [نسخهٔ اصلی Design](02-design/v001-original.md).

رشتهٔ body بسته نشده و تعریف bodyFa و یک عبارت دیگر داخل آن افتاده است. نمونهٔ استخراج‌شده با JSON.parse نامعتبر تشخیص داده شد. مدل هم‌زمان دستور JSON معتبر و نمونهٔ نامعتبر دریافت می‌کند. اصلاح نمونه و یکسان‌سازی قرارداد همهٔ ایجنت‌ها قبل از تنظیم جزئیات نگارشی اولویت دارد.

### ۴. درخواست industry بدون وجود دادهٔ مجاز

هر سه متخصص و QA عبارت `allowedTaxonomies.industries` و فیلد `industry` دارند؛ اما [سرور](../server.ts) تنها شش محور intents/domains/tools/languages/difficulties/outputFormats می‌فرستد. `industry` نیز در [نوع Prompt](../src/types.ts) و نگاشت خروجی تحلیل در [فرم](../src/pages/AdminPromptAddEdit.tsx) مصرف نمی‌شود.

این ناسازگاری قطعیِ قرارداد است؛ رفتار expression مربوط به مقدار ناموجود در نسخهٔ n8n اجرا نشده است. پیشنهاد این مرحله حذف industry از قرارداد این ورک‌فلو است، مگر اینکه مالک توسعهٔ جداگانهٔ این مفهوم در محصول را بخواهد.

### ۵. متن literal با expression در QA تداخل دارد

در متن expression-mode نود QA، عبارت `{{placeholder_key}}` به عنوان مثال نوشته شده است. طبق [مستند expressions](https://docs.n8n.io/build/work-with-data/expressions-versus-data-nodes.md)، همین نشانه برای ارزیابی JavaScript در پارامتر استفاده می‌شود. در export، متغیر `placeholder_key` تعریف نشده است.

وجود expression زائد با بررسی متن تأیید شد؛ اثر دقیق runtime، خطا یا مقدار ناموجود، هنوز آزمایش نشده است. پیشنهاد: در دستورهای داخل n8n از `[[placeholder_key]]` به صورت literal استفاده شود یا curly brace با روش مناسب expression تولید شود. تبدیل فعلی سایت از `[[...]]` به `{{...}}` وجود دارد؛ استفاده از براکت مربعی در پرامت ایجنت‌ها به‌خودی‌خود ایراد نیست.

## تعارض‌های مؤثر بر کیفیت پرامت

### Design

- «حفظ دقیق تعداد کلمه و همهٔ متن» با جایگزینی عبارت‌های چندکلمه‌ای، اصلاح دستور زبان و افزودن `--ar` سازگار نیست. حفظ معنا، قیود و جزئیات معیار مناسب‌تری از برابر بودن تعداد کلمات است.
- افزودن اجباری `--ar [[aspect_ratio]]` بدون شناسایی ابزار، متن عمومی را به نحو یک موتور خاص نزدیک می‌کند؛ با قواعد انتخاب گستردهٔ ابزارها نیز تعارض ایجاد می‌کند. پارامتر تازه باید متناسب با ابزار و هدف باشد.
- دستور «۴ تا ۶ متغیر» می‌تواند به متغیرسازی زائد در ورودی کوتاه یا حذف انتخاب مفید در متن بلند منجر شود. تعداد تابع نیاز واقعی کاربر باشد.
- دستور مرجع تصویر می‌گوید placeholder نساز، ولی قاعدهٔ ۱۸ برای `[[image_reference]]` schema می‌خواهد. تشخیص مرجع فایل پیوست و دریافت URL دو رفتار جدا هستند و باید صریح انتخاب شوند.
- جایگزینی شدت کیفی مانند subtle با slider عددی ۱ تا ۱۰ می‌تواند عبارت نامفهوم بسازد؛ UI فعلی مقدار عددی را مستقیماً در متن جایگزین می‌کند و تبدیل آن به عبارت کیفی ندارد.
- duration، frame rate و shot length در یک دستور به `duration_seconds` نگاشت شده‌اند؛ ثانیه و فریم‌برثانیه یک پارامتر نیستند.
- الزام بدنهٔ انگلیسی با تشخیص زبان واقعی در مسیریاب هماهنگ نشده است. سیاست زبان متن اصلی و ترجمه باید مشخص باشد.

### programming و general

- حفظ جزئیات، ممنوعیت دست‌کاری کد و انتخاب متغیرهای مرتبط، قواعد مفید فعلی هستند.
- قرارداد FieldSchema کامل بیان نشده است: نوع‌های مجاز، معنی required، بازهٔ slider و رفتار مقدارهای گزینه‌ها در همهٔ شاخه‌ها یکسان نیستند. وجود گزینهٔ انتخابی به‌تنهایی کاربردپذیری فیلد را تضمین نمی‌کند.
- هر دو bodyFa را از schema حذف کرده‌اند، اما QA تولید آن را برای همه لازم می‌داند. مسئول ترجمه باید روشن باشد تا تولید و بازنویسی تکراری کاهش یابد.
- گزینهٔ فارسی خالص داخل پرامت انگلیسی مستقیماً جایگزین می‌شود؛ پیشنهاد `value|label` باید بر اساس زبان خروجی و نوع مفهوم تعیین شود، نه فقط فنی بودن نام.

### QA/Verifier

- هم دستور «بدون کلید اضافه و همان schema» دارد و هم الزام تولید bodyFa؛ نمونهٔ نهایی bodyFa و requiresReferenceImage را ذکر نمی‌کند. ریسک حذف/اضافهٔ ناهماهنگ وجود دارد.
- ویدیو را مشروط به وجود placeholder حرکتی/زمانی کرده است. پرامت ویدیویی معتبر می‌تواند حرکت ثابت و غیرقابل شخصی‌سازی داشته باشد. تشخیص نوع خروجی باید بر متن خام و معنای حرکت متکی باشد، نه الزام ساخت متغیر.
- دستور افزودن ابزارهای عمومی ممکن است با شرط «فقط گزینهٔ مجاز درخواست» رقابت کند. شرط عضویت در فهرست باید در تمام اصلاحات مقدم باشد؛ قابلیت ابزار بدون شاهد اجرای واقعی، نشان آزموده‌شده ایجاد نمی‌کند.
- بازبینی اکنون هم اصلاح ساختار، ترجمه، انتخاب ابزار و بازنویسی محتوا را بر عهده دارد. پیشنهاد: کنترل ساختاری قطعی به Code سپرده شود و QA روی وفاداری معنایی، تناسب گزینه‌ها و کیفیت ترجمه تمرکز کند.
- دستورها و متن خام در یک پارامتر text قرار گرفته‌اند؛ System Message سفارشی در export دیده نمی‌شود. برای تفکیک درخواستِ قابل پردازش از قواعد پردازش، قواعد ثابت به پیام System و متن خام/خروجی متخصص به بخش‌های دادهٔ مشخص منتقل شوند. رفتار پیام پیش‌فرض runtime بررسی نشده است.

## مسیریاب و دامنهٔ اتصال

- تقسیم سه خانواده روشن است، اما تکلیف تولید صوت، موسیقی و موارد چندرسانه‌ای مرکب باید با نمونه تعیین شود؛ صرف افتادن در general تضمین تخصص کافی نیست.
- content_type، source_language، confidence و note به عنوان متن ورودی متخصص/QA درج نمی‌شوند؛ متخصص‌ها دوباره به متن Webhook رجوع می‌کنند. تنها routing_category در تصمیم Switch مصرف می‌شود. یا این داده‌ها برای هدفی مشخص استفاده شوند یا تولید بی‌مصرفشان کم شود.
- confidence در هیچ مسیر تصمیم‌گیری یا fallback استفاده نمی‌شود و معیار اندازه‌گیری کیفیت نیست.
- parser فعلی از JSON example ساخته شده است؛ طبق [مستند رسمی](https://docs.n8n.io/integrations/builtin/cluster-nodes/sub-nodes/n8n-nodes-langchain.outputparserstructured/)، نام و نوع فیلدها را می‌گیرد و مقدارهای نمونه را نادیده می‌گیرد. بنابراین enum سه category و بازهٔ confidence با همین مثال تضمین نمی‌شود.
- این export برای `analyze_source` طراحی شده است. action ورودی بررسی نمی‌شود؛ برای درخواست `refine_prompt` که `originalPrompt` دارد و taxonomy ندارد، سازگار نیست. اتصال همین webhook به هر دو تنظیم سایت نیازمند طراحی مسیر جداست.
- فاصلهٔ useCase/resourceType با فرم جدید که در [بررسی اولیه](initial-review.md) آمده، همچنان برقرار است؛ صرف افزودن آن‌ها به متن ایجنت کافی نیست.

## ترتیب پیشنهادی اصلاح

۱. یکسان‌سازی دادهٔ Router/Switch، مسیر خطای صریح و اصلاح نمونهٔ خراب Design.
۲. تعریف قرارداد مشترک خروجی مطابق محصول؛ تعیین bodyFa، requiresReferenceImage، زبان و حذف industry بدون مصرف.
۳. اصلاح Code برای حفظ متن و اعتبارسنجی قطعی schema، متغیرها و taxonomy.
۴. بازنویسی نسخه‌دار دستورها: حذف قواعد متناقض، تفکیک System و داده، جلوگیری از متغیرسازی و نحو ابزارِ بی‌دلیل.
۵. مقایسهٔ قبل/بعد با ورودی ثابت برای هر سه شاخه، تصویر مرجع، ویدیو، بلوک کد و متن فارسی/انگلیسی؛ ثبت کیفیت، زمان کل و مصرف توکن واقعی.

به دلیل نبود ابزار/حافظهٔ متصل، امکان ساده‌سازی متخصص‌ها و QA به LLM Chain قابل بررسی است؛ تغییر نوع نود و حذف QA هنوز تصمیم نهایی نیست. مستند n8n نیز برای خروجی ساختاریافتهٔ Agent، استفاده از chain جدا را پیشنهاد می‌کند؛ [توضیح رسمی](https://docs.n8n.io/integrations/builtin/cluster-nodes/sub-nodes/n8n-nodes-langchain.outputparserstructured/common-issues/). اندازه‌گیری کیفیت قبل از کاهش مراحل لازم است.

## حدود اعتبارسنجی

ساختار فایل، اتصالات، متن همهٔ پرامت‌ها و قرارداد برنامه بررسی شد؛ هفت بازآفرینی JavaScript/JSON محلی انجام شد. هیچ درخواست مدل، اجرای n8n، تغییر وب‌هوک، دیپلوی، commit یا push انجام نشده است. [نتایج بازآفرینی](verification.md) شواهد خطاهای قطعی را از ریسک‌های نیازمند اجرای واقعی جدا می‌کند.
