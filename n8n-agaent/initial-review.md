# بررسی اولیهٔ ارتباط پرامتی و n8n

این سند پیش از دریافت export تهیه شده است. یافته‌های مربوط به ورک‌فلوی ارسالی و پرامت‌های واقعی در [گزارش بررسی ورک‌فلو](workflow-review.md) و [فهرست آرشیو](README.md) ثبت شده‌اند؛ عبارت‌های «هنوز دریافت نشده» در این سند به مرحلهٔ اولیه اشاره دارند.

تاریخ: ۲۰۲۶-۱۰-۱۷. مبنای کد: `release` در `7e0677057644ccd53d5b26addb5e5b080f59184d`؛ HEAD محلی و برنچ راه‌دور GitHub در زمان بررسی با این شناسه برابر بودند. آخرین کامیت مربوط به لوگوی متحرک قابل تنظیم است؛ قرارداد n8n از وضعیت کل کد در همین کامیت استخراج شده است.

این بررسی خواندنیِ کد و آماده‌سازی آرشیو است. اجرای وب‌هوک، کیفیت مدل یا وضعیت زندهٔ n8n را تأیید نمی‌کند. تغییرات موجود کاربر در اسناد پروژه حفظ شده‌اند.

## مسیر اصلی: متن خام به رکورد قابل ویرایش

شواهد: [مسیرهای سرور](../server.ts)، بخش `/api/analyze-source`؛ [فرم مدیریت](../src/pages/AdminPromptAddEdit.tsx)، تابع `handleAnalyzeSource`.

۱. مدیر در فرم افزودن/ویرایش، `sourceText` را وارد می‌کند.
۲. فرم با احراز هویت مدیر به `POST /api/analyze-source` درخواست می‌دهد.
۳. سرور در صورت تنظیم `n8nAnalyzeWebhook`، متن و گزینه‌های مجاز دسته‌بندی را به n8n می‌فرستد.
۴. پاسخ n8n باز می‌شود و داخل `{ success: true, data: ... }` به فرم برمی‌گردد.
۵. فرم عنوان، توضیح، متن، فیلدهای شخصی‌سازی و تعدادی از فراداده‌ها را پر می‌کند؛ ذخیرهٔ رکورد اقدام جداگانهٔ مدیر است.

بدنهٔ درخواست سرور به n8n:

```json
{
  "sourceText": "متن خام ورودی",
  "allowedTaxonomies": {
    "intents": "رشتهٔ گزینه‌ها با جداکنندهٔ ویرگول",
    "domains": "رشتهٔ گزینه‌ها با جداکنندهٔ ویرگول",
    "tools": "رشتهٔ گزینه‌ها با جداکنندهٔ ویرگول",
    "languages": "رشتهٔ گزینه‌ها با جداکنندهٔ ویرگول",
    "difficulties": "رشتهٔ گزینه‌ها با جداکنندهٔ ویرگول",
    "outputFormats": "رشتهٔ گزینه‌ها با جداکنندهٔ ویرگول"
  },
  "action": "analyze_source",
  "timestamp": "زمان درخواست به صورت ISO"
}
```

این مثال شکل داده را نشان می‌دهد؛ مقادیر دسته‌بندی نمونهٔ واقعی یا فهرست مجاز نیستند. سرور گزینه‌ها را از taxonomyهای فعال می‌گیرد و در نبود گزینه برای هر محور از ثابت‌های داخلی استفاده می‌کند. مقدارهای `allowedTaxonomies` رشته‌اند، نه آرایه؛ ایجنت باید گزینه‌های همان درخواست را رعایت کند. در حالت عادی مقدارها slug هستند، اما fallback داخلی ممکن است قالب متفاوتی داشته باشد؛ فهرست ثابت در پرامت ایجنت جای دادهٔ درخواست را نگیرد.

## قرارداد خروجی تحلیل که فرم مصرف می‌کند

| فیلد | نوع مورد انتظار در مسیر فعلی | مصرف |
|---|---|---|
| `title`, `description` | string | معرفی پرامت در فرم |
| `body` | string | متن پرامت با متغیرهای قابل شخصی‌سازی |
| `bodyFa` | string، در صورت ارائه | نسخهٔ فارسی متن |
| `fieldsSchema` | array از FieldSchema | ساخت فرم شخصی‌سازی |
| `intent` | string | هدف اصلی؛ با قواعد آرشیو نرمال می‌شود |
| `intents` | string[]، در صورت ارائه | اهداف چندانتخابی؛ در نبود آن از intent استفاده می‌شود |
| `domains`, `tools`, `outputFormats` | string[] | فیلترهای مکمل؛ انتخاب از گزینه‌های درخواست |
| `task`, `language`, `difficulty` | string | فرادادهٔ پرامت |
| `tags` | string[] | برچسب‌ها |
| `requiresReferenceImage` | boolean، در صورت ارائه | نیاز به تصویر مرجع |

این جدول انتظار مصرف‌کننده است؛ سرور برای پاسخ n8n اعتبارسنجی کامل schema ندارد. قالب نهایی پیشنهادی برای ورک‌فلو بعد از دریافت خروجی واقعی و Parser آن تعیین می‌شود. پیشنهاد اولیه: یک JSON object مستقیم و بدون متن توضیحی یا حصار Markdown برگردد.

سرور همچنین آرایه را با برداشتن عضو اول، `output` شیء یا رشتهٔ JSON و `text` رشتهٔ JSON می‌خواند. فیلدهای قدیمی `tool/domain/outputFormat` به آرایه تبدیل می‌شوند. این انعطاف جای قرارداد دقیق خروجی را نمی‌گیرد.

## متغیرها و فرم شخصی‌سازی

شواهد: [FieldSchema](../src/types.ts)، [جایگزینی متغیرها](../src/lib/renderPrompt.ts)، [فرم و کنترل پیش از کپی](../src/components/PromptWizard.tsx).

- قالب پیشنهادی متغیر `{{product_name}}` است؛ کلیدها ASCII و snake_case با الگوی `^[a-z][a-z0-9_]*$` باشند. این قاعده در پرامت داخلی سرور هم آمده است؛ renderer فعلی فقط `\w+` را تشخیص می‌دهد.
- برای هر کلید قابل شخصی‌سازی، یک فیلد متناظر و یکتا در `fieldsSchema` لازم است؛ فیلد بدون کاربرد در متن تولید نشود. این معیار پیشنهادی کیفیت است، نه تضمین اعتبارسنجی فعلی سرور.
- هر فیلد حداقل `key`, `label`, `type` دارد. نوع‌های موجود: `text`, `textarea`, `color`, `select`, `radio`, `switch`, `slider`, `multiselect`, `url`.
- برای نوع‌های انتخابی `options` و برای slider بازهٔ معنادار `min/max` لازم است. عنوان و راهنمای فرم برای کاربر فارسی باشد.
- فرم گزینه‌های `value | label` را نیز می‌خواند؛ مقدار سمت چپ وارد پرامت می‌شود و سمت راست نمایش داده می‌شود. زبان مقدار نهایی باید با متن پرامت هماهنگ باشد.
- اگر `bodyFa` ارائه می‌شود، کلیدهای متغیر آن با متن اصلی و schema هماهنگ بمانند.
- پیش از کپی، حتی متغیری که فیلدش اختیاری است اگر در متن باقی بماند باعث خطای تکمیل می‌شود. افزودن متغیر زائد، تکمیل فرم را دشوار می‌کند.

## فاصلهٔ قرارداد فعلی با آرشیو جدید

آرشیو محصول بر `useCase` و `resourceType` تکیه دارد؛ [تعریف آرشیو](../src/lib/archiveCatalog.ts). اما درخواست تحلیل به n8n فهرست کاربردها و انواع منبع را نمی‌فرستد و `handleAnalyzeSource` نیز این دو را از پاسخ وارد فرم نمی‌کند. مدیر فعلاً کاربرد را جداگانه انتخاب می‌کند. افزودن این دو کلید به پرامت ایجنت به‌تنهایی این فاصله را رفع نمی‌کند.

همچنین مسیر تحلیل در صورت نبود وب‌هوک و وجود کلید Gemini از پرامت داخلی سرور استفاده می‌کند. این متن، پرامت ایجنت n8n نیست. اگر وب‌هوک تنظیم شده باشد اما شکست بخورد، مسیر تحلیل خطا برمی‌گرداند و به Gemini جابه‌جا نمی‌شود.

## مسیر دوم: ارتقای متن آماده

شواهد: `POST /api/refine-prompt` در [سرور](../server.ts).

- ورودی به n8n: `promptId`, `originalPrompt`, `action: "refine_prompt"`, `timestamp`.
- این مسیر `allowedTaxonomies` یا `fieldsSchema` را ارسال نمی‌کند و قرارداد آن متن ارتقایافته است.
- شکل سادهٔ پیشنهادی پاسخ: `{ "refinedPrompt": "متن ارتقایافته" }`. سرور شکل‌های دیگری از جمله `output/text/refined` و رشتهٔ مستقیم را هم می‌خواند؛ نبود اعتبارسنجی دقیق ممکن است دادهٔ نامناسب را بپذیرد.
- در نبود وب‌هوک یا خطای آن، متن اصلی با `success: true` و `fallbackUsed: true` برمی‌گردد؛ موفقیت HTTP به معنی بهینه‌سازی موفق نیست.
- در جست‌وجوی کد فعلی `src` فراخوانی این endpoint در رابط پیدا نشد؛ وجود مسیر سرور و تنظیم آن، شاهد استفادهٔ جاری در رابط نیست.
- هر دو مسیر محدودیت زمان تنظیم‌پذیر دارند: پیش‌فرض ۶۰ ثانیه، محدود به ۱۰ تا ۳۰۰ ثانیه. تعداد و ترتیب واقعی ایجنت‌ها باید در ارزیابی زمان کل لحاظ شود.

## محور بررسی پس از دریافت ورک‌فلو

ابتدا نسخهٔ واقعی هر ایجنت و قرارداد بین نودها ثبت می‌شود. سپس حفظ هدف و قیود متن خام، مسئولیت مشخص هر مرحله، حذف پردازش تکراری، تولید JSON معتبر، تطابق schema و متغیرها، دسته‌بندی بر اساس گزینه‌های واقعی و کیفیت متن نهایی با نمونه‌های قبل/بعد ارزیابی می‌شود. مدل، تعداد ایجنت‌ها و بهبود زمان یا هزینه تا دریافت شواهد قطعی نیستند.

در این مرحله فقط سه فایل Markdown آرشیو ایجاد شده‌اند؛ کد محصول و ورک‌فلوی n8n تغییر نکرده‌اند. آزمون زنده یا تست کیفیت ایجنت اجرا نشده است.
