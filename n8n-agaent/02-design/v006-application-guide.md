# راهنمای آزمون Design v006 و QA v005

تاریخ: ۲۰۲۶-۱۰-۱۸. وضعیت متن‌ها: proposed / آماده برای آزمون مالک. این فایل گزارش استقرار نیست. دستور مالک، تألیف نسخه جدید این دو ایجنت را مجاز کرده است؛ تأیید متن دقیق یا اعمال زنده از آن نتیجه نمی‌شود.

## فایل‌های کامل برای جایگزینی

| نود | System Message، حالت Fixed | Prompt / User Message، حالت Expression در ویرایشگر |
|---|---|---|
| Design | [system-message.txt](system-message.txt) | [user-message-editor.txt](user-message-editor.txt) |
| QA/Verifier | [System](../05-qa-verifier/system-message.txt) | [User](../05-qa-verifier/user-message-editor.txt) |

این نسخه عمداً از پیام یکپارچه نسخه پیشین به System ثابت و User ورودی جدا تبدیل شده است. متن قدیمی Prompt را نگه ندارید یا به متن جدید اضافه نکنید. System سفارشی این نسخه خالی نیست.

فایل user-message.txt مقدار دقیق قابل ذخیره در export را با پیشوند = دارد؛ فایل user-message-editor.txt دقیقاً همان مقدار بدون اولین = است. برای ویرایشگر حالت Expression، فایل دوم را کپی کنید. {{ ... }} در آن عبارت ورودی n8n است. System در حالت Fixed قرار می‌گیرد. current.md و snapshot شامل دو مقدار کامل و SHA-256 مستقل هستند. هیچ تغییر زنده‌ای از Codex انجام نشده است.

## چه چیزی تغییر کرده است؟

- کار و نتیجه کاربر مبنای طبقه‌بندی است: useCase یک شناسه واقعی، relatedUseCases صفر تا دو شناسه مرتبط، resourceType یکی از prompt/skill/agent-guide.
- فهرست ۱۷۰ کاربرد رسمی مخزن در هر دو System قرار دارد تا با Webhook فعلی که فهرست کاربرد نمی‌فرستد هم آزمون مستقل ممکن شود. ۹ گروه مادر و زیرگروه معرفی محصول حفظ شده‌اند؛ شناسه‌های legacy وارد انتخاب‌های جدید نشده‌اند. این‌ها snapshot هستند، نه فهرست زنده.
- catalogVersion به پایه release-7e06770-2026-10-18 ارجاع می‌دهد. بعداً classificationCatalog معتبرِ ورودی می‌تواند جایگزین کامل آن شود. فهرست صریح خالی نباید با fallback دور زده شود.
- دلیل طبقه‌بندی، ابهام‌ها و نیاز به بازبینی در editorial است؛ این بخش وارد متن قابل کپی پرامپت نمی‌شود.
- قابلیت موردنیاز از نام ابزار جداست. مسیر اجرایی نامشخص با routes:[] و tools:[] ثبت می‌شود. این مقدار ادعای ناسازگاری با همه ابزارها نیست.
- وضعیت tested فقط با شاهد ساختاریافته ورودیِ مطابق همان محیط، مدل، تاریخ و نتیجه مجاز است. حدس ایجنت یا ادعای خود candidate شاهد نیست.
- کنترل‌ها باید مفید، سازگار و از نظر دستوری پس از جایگذاری درست باشند. هیچ سهمیه عمومی برای تعداد فیلد تعیین نشده است.
- نگاشت واقعی گزینه‌های فارسی در صفحه جزئیات از کد خوانده شده: قسمت پس از | برای گزینه منطبق غیرعددی جایگذاری می‌شود. پیش‌نمایش فرم و ورودی آزاد الزاماً چنین ترجمه‌ای ندارند.
- QA روی شاخه‌های برنامه‌نویسی و عمومی هم دریافت دارد؛ قواعد تصویری را به آن‌ها تحمیل نمی‌کند. متن آن متخصص‌ها در این مرحله تغییر نکرد.

## مرز سازگاری با سایت و سایر نودها

قرارداد promty-editorial-v1 شامل ۱۴ کلید قدیمی به‌علاوه useCase، relatedUseCases، resourceType و editorial است؛ در مجموع ۱۸ کلید. خروجی همچنان یک شیء است.

| جزء | مشاهده در کد/آرشیو فعلی | اثر برای این آزمون |
|---|---|---|
| Webhook از سایت | allowedTaxonomies شش محور می‌فرستد؛ کاربردها و نوع منبع را نمی‌فرستد | snapshot تعبیه‌شده این مرحله را پوشش می‌دهد |
| Design و QA | متن کامل جدید آماده است | باید توسط مالک در دو نود جایگزین و واقعاً اجرا شود |
| Code اصلی export اول | فهرست بسته برای root ندارد، ولی مشکلات قدیمی parse دارد | این بررسی، سلامت یا فعال‌بودن آن را تأیید نمی‌کند |
| Code پیشنهادی v002 | rootKeys بسته و قدیمی دارد | خروجی جدید را با unsupported root property رد می‌کند؛ در این مرحله تغییر نکرد |
| فرم AdminPromptAddEdit | useCase/resourceType برگشتی تحلیل را اعمال نمی‌کند؛ related/editorial را هم نمی‌خواند | فعلاً نتیجه این فیلدها را در خروجی مستقیم QA بررسی کنید |
| ذخیره‌سازی | کاربرد اصلی و نوع منبع موجود است؛ مرتبط‌ها/راهنمای اجرا قرارداد تازه می‌خواهند | تکمیل اتصال در مرحله بعد؛ تأیید ذخیره خودکار این فیلدها نیست |
| programming/general/Router | متن‌ها حفظ شده‌اند | تغییر آن‌ها خارج از این نسخه است |

نسخه جاری Code در n8n مشاهده نشده است. اگر مرحله Code خطا داد، ابتدا خروجی مستقیم QA را جدا بررسی کنید. رفع این ناسازگاری با نسخه تازه Code و اتصال فرم کار بعدی است؛ این فایل آن تغییرات را اعمال نمی‌کند.

## آزمون عکس به کارتون

فایل‌های نمونه در [بسته v006](examples/v006/) هستند:

- photo-to-cartoon-source.txt: متن اصلی آزمون، بدون اجرای درخواست تولید تصویر.
- received-n8n-output.json: پاسخ ارسالی مالک، برای مقایسه؛ محصول نسخه تازه نیست.
- test-input.json: بدنه نمونه Webhook با فهرست‌های آزمایشی و بدون اطلاعات محرمانه. output نود Webhook باید این بدنه را در json.body داشته باشد.
- classification-catalog.json: فهرست کامل snapshot.
- reference-output.json: نمونه مرجع دست‌نویس؛ خروجی واقعی n8n یا مدل نیست.
- rendered-combinations.json: ۹ ترکیب همان مرجع در دو زبان؛ ۱۸ متن نهایی.
- validation-report.json / expression-report.json: نتیجه بررسی محلی، با محدودیت‌های صریح.

ابتدا همین sourceText را با مسیر واقعی Design → QA اجرا کنید. نام نود Webhook در expressionها عین نام export دریافت‌شده حفظ شده است. اگر نام نود در محیط شما متفاوت است، فقط ارجاع همان نام را هماهنگ کنید؛ متن خروجی ساخته‌شده را جای source نگذارید.

برای این نمونه انتظار داریم:
1. useCase برابر vis-09؛ نوع منبع prompt؛ عکس مرجع لازم؛ خروجی image.
2. صفر تا دو مرتبطِ واقعی؛ vis-04 مجاز و اختیاری است. هیچ الزام برای پرکردن سه مورد وجود ندارد.
3. دو کنترل خط دور و سایه‌زنی مفیدند؛ کنترل اضافه فقط با منفعت مستقل و سازگاری. همه کلیدها و تعداد تکرارشان در دو زبان یکسان باشند.
4. تناسبات اصلی بدن با ظاهر بامزه تعارض نداشته باشد؛ مثال‌های صحنه فقط در صورت وجود اعمال شوند؛ پاستلی‌شدن باعث تغییر هویت رنگ لباس یا پوست نشود.
5. تمام گزینه‌ها در جمله فارسی/انگلیسی روان باشند؛ نمونه عبارت خراب «با ضخامت خط دستی با تغییرات ظریف ضخامت» باقی نماند.
6. بدون شاهد اجرا، مسیر tested و تاریخ/مدل/شاهد ساختگی وجود نداشته باشد. tools:[] و routes:[] برای این منبع عمومی قابل قبول است.
7. توضیح محتوا نتیجه را تضمین نکند؛ metadata و editorial از بدنه جدا باشند.
8. خروجی مستقیم Design و خروجی QA را جدا ذخیره کنید تا معلوم شود هر اصلاح در کدام مرحله اتفاق افتاده است. زمان اجرا و مدل واقعی را کنار نتیجه ثبت کنید.

موارد مرزی برای اجرای واقعی بعدی: QA با candidate دارای کاربرد ساختگی، بیش از دو کاربرد مرتبط، نوع Skill برای پرامپت ساده، گزینه ناسازگار، عبارت فارسی شکسته، fieldsSchema خالی با امکان کنترل مفید، و ادعای tested بی‌شاهد. QA باید آن‌ها را اصلاح کند؛ صرف پاس‌بودن JSON کافی نیست.

## بررسی‌هایی که واقعاً اجرا شدند

بررسی ساختاری با Python، ارزیابی expressionها با JavaScript VM و داده ساختگی، تطابق ۱۷۰ شناسه با مخزن، جایگذاری ۹ ترکیب در دو زبان، و probe خواندنی ناسازگاری Code v002. آزمون‌های ساختاری توانایی مدل در رعایت دستورها را ثابت نمی‌کنند. متن مرجع از نظر معنایی و عبارت‌های جایگذاری‌شده بازخوانی شد؛ ارزیابی زبان طبیعی خودکار نیست.

برای بازاجرای بررسی‌های محلی، از پوشه مثال v006 اجرا کنید:

    python3 validate_contract.py
    node verify_expressions.cjs

این دو فایل ابزار آزمون محلی‌اند، نه جایگزین نود Code. فایل legacy-code-v002.input.js تنها یک fixture از متن تاریخی برای نشان‌دادن مرز سازگاری است.

هیچ فراخوانی n8n، LLM یا مدل تصویر، تغییر دیتابیس/برنامه/سرور، Commit یا Push انجام نشده است. پس از اجرای مالک، متن دقیق دو نود یا export و خروجی‌های Design/QA مبنای ثبت شاهد و نسخه بعدی خواهد بود. نسخه‌های قبلی و exportهای اصلی دست‌نخورده‌اند.
